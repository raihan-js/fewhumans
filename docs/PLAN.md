## 1. The problem and the idea

### 1.1 The problem

Researchers (Raihan included, in FedProc, OracleBench and EditBench) use LLMs as judges and labelers because human experts are expensive or unavailable. Then they report results computed from judge labels. That has two failures:

- **Bias:** the judge's errors flow straight into the reported number. A judge that prefers long answers inflates a system's score; a judge that misses rare classes deflates recall.
- **No defensible uncertainty:** a confidence interval computed on judge labels describes the judge, not the truth.

The usual fix, "label a random 100 by hand to check the judge", is ad hoc: nobody knows whether 100 is enough, which 100 to pick, or how to combine those 100 with the 5,000 judge labels.

### 1.2 The idea

**FewHumans** is a library that sits between LLM judges and human annotators and does three things with valid statistics:

1. **Routes:** decides which items a human should label next (random, stratified by judge agreement, or active sampling by judge uncertainty and disagreement), always with known sampling probabilities so estimates stay unbiased.
2. **Estimates:** combines few human labels with many judge labels using prediction-powered inference (PPI, PPI++) and active statistical inference, giving an estimate and a confidence interval that remain valid even when the judges are biased.
3. **Stops:** uses **anytime-valid confidence sequences**, so the researcher can look at the interval after every human label and stop as soon as it is narrow enough, without breaking validity. (Re-checking an ordinary fixed-sample interval after every label inflates the error rate; Phase 4 measures how much.)

It also produces a **judge report card**: agreement with humans by slice, where the judge fails, the cost per estimate, and whether the judge could replace humans for this task (the Alternative Annotator Test).

### 1.3 What already exists (cite, don't claim)

Verified on 9 Oct 2026; re-verify and read each before writing the paper:

- Angelopoulos et al., *Prediction-Powered Inference* (arXiv 2301.09633) and *PPI++: Efficient Prediction-Powered Inference* (arXiv 2311.01453); reference implementation `ppi_py` (github.com/aangelopoulos/ppi_py).
- Zrnic & Candès, *Active Statistical Inference* (arXiv 2403.03208): choosing which items to label by model uncertainty, with valid inference.
- Gligorić, Zrnic, Lee, Candès, Jurafsky, *Can Unconfident LLM Annotations Be Used for Confident Conclusions?* (NAACL 2025, arXiv 2408.15204): confidence-driven inference with LLM annotations.
- Calderon, Reichart, Dror, *The Alternative Annotator Test for LLM-as-a-Judge* (ACL 2025, arXiv 2501.10970): when an LLM can statistically replace human annotators.
- Sfyraki & Wang, *Revisiting Active Sequential Prediction-Powered Mean Estimation* (ICLR 2026, arXiv 2604.18569): **found that uncertainty-based query rules often give little advantage over a near-uniform rule**, and gave a non-asymptotic, anytime bound via Freedman's inequality.
- Confidence sequences and anytime-valid inference (for example Waudby-Smith & Ramdas, betting-based confidence sequences; Howard et al., time-uniform bounds). Find the exact papers.
- Existing LLM-eval tools (DeepEval, Evidently, `judges`, others; also check `evalhawk`, which has an issue titled "PPI correction"). Survey them and state precisely what FewHumans adds.

### 1.4 What is new (the contribution, if results support it)

1. **A practical, tested toolkit** that puts routing, PPI/active inference, anytime-valid stopping, multi-judge panels and judge report cards into one workflow a non-statistician researcher can run, with coverage-tested defaults.
2. **A large empirical study on real annotation tasks** with realistic multi-judge panels (local open models plus API models): for a fixed human budget, which routing and estimation strategy gives the narrowest intervals that still cover the true value 95% of the time?
3. **Multi-judge disagreement as the routing signal** (not only a single model's confidence), tested against uniform sampling. Given Sfyraki & Wang, the honest hypothesis is open: disagreement routing may or may not beat uniform. Either result is publishable.
4. **Measured harm of current practice:** how often judge-only estimates and "peeking" at fixed intervals give confidently wrong conclusions on real tasks.

## 5. Phase 1 — Core library design (~3 days)

### 5.1 Concepts

- **Item:** an object to be labeled (text, a pair of responses, a span, an image path). Has `item_id`, `payload`, optional `strata` (any user metadata).
- **Label space:** `binary`, `categorical(K)`, `ordinal(1..K)`, `real`, `pairwise` (A/B/tie).
- **Judge:** anything that maps an item to a label plus optional confidence. Built-ins: LLM judge (OpenAI-compatible or Anthropic), with prompt template, model ID, temperature, and confidence method (`verbalized`, `logprob` where the API exposes it, `self_consistency(k)`); `python` judge (any function, e.g. a classifier); `oracle` judge (a deterministic checker that is exactly correct on the items it covers, such as a registry lookup; used as a free "human" label only on the items where it applies, and the user must assert exactness).
- **Panel:** a list of judges. Panel outputs: each judge's label and confidence, the panel's majority/mean, and **disagreement** (entropy of the vote, or variance for real/ordinal labels).
- **Estimand:** what the researcher wants: `mean` (e.g. accuracy of a system = mean of correctness labels, average rating), `proportion` per class, `difference` between two systems (paired), `win_rate` (pairwise), `ratio` estimands such as precision and recall (via delta method or a validated bootstrap; must pass coverage), and `regression` coefficients (via `ppi_py`, optional).
- **Human label:** a label from a person, with `annotator_id`, `timestamp`, and the **sampling probability** with which the item was selected.
- **Session:** holds items, panel outputs, the routing policy, the human labels and the estimate history. Saved as a folder of Parquet + JSON so it can be resumed.

### 5.2 Public API (target)

```python
import fewhumans as fh

task = fh.Task(label_space=fh.Categorical(["correct", "incorrect"]),
               estimand=fh.Mean(of=lambda y: y == "correct"))  # accuracy

panel = fh.Panel([
    fh.LLMJudge("local-qwen", base_url=..., model="Qwen/Qwen2.5-7B-Instruct",
                prompt=fh.Prompt.from_file("judge.md"), confidence="logprob"),
    fh.LLMJudge("haiku", provider="anthropic", model="<pinned id>",
                prompt=fh.Prompt.from_file("judge.md"), confidence="verbalized"),
])

s = fh.Session.create("runs/my_eval", items=items, task=task, panel=panel,
                      routing=fh.routing.Active(signal="disagreement", budget=300),
                      confidence=0.95, sequential=True)
s.run_panel(max_cost_usd=5)            # judges label everything, with cost tracking

for item in s.queue(n=20):             # next items for humans, with known probabilities
    s.add_human(item.item_id, label=ask_a_human(item), annotator="raihan")

est = s.estimate()                     # value, interval, n_human, method, anytime_valid
print(est)                             # e.g. "accuracy 0.812 [0.789, 0.836], 140 human labels"
s.should_stop(target_halfwidth=0.02)   # True/False with explanation
s.report("report.html")                # judge report card + estimate history
```

### 5.3 CLI (same features, file-based)

```
fewhumans init runs/x --items items.jsonl --task task.yaml --panel panel.yaml
fewhumans judge runs/x --max-cost 5
fewhumans queue runs/x --n 20 > to_label.jsonl     # or: fewhumans label runs/x (Streamlit UI)
fewhumans add runs/x labels.jsonl
fewhumans estimate runs/x
fewhumans report runs/x --html report.html
```

Import/export: JSONL and CSV; optional Label Studio export/import (only if it stays a thin adapter).

### 5.4 Judge execution

- Async, rate-limited, retry with backoff, cached on disk by `(judge config hash, item hash)` so re-runs are free.
- Cost and latency recorded per call (token counts × a price table the user can edit; never hard-code prices as facts in docs).
- Output parsing with a strict schema; parse failures recorded as `ABSTAIN` with the raw text, never silently coerced.
- Temperature 0 by default; `self_consistency(k)` uses temperature > 0 and records all samples.

**Checkpoint 1:** API sketch running end to end on a toy dataset with a fake judge (no real models yet), session save/resume, CLI round trip.

## 6. Phase 2 — Estimators and routing (~4 days)

### 6.1 Estimators (each with a docstring citing the source equations)

| id | estimator | interval |
|---|---|---|
| E0 | **judge-only**: estimand computed on panel labels | naive CLT (included to measure its failure; never the default) |
| E1 | **human-only**: classical estimate on the human sample | CLT / Wilson / exact |
| E2 | **PPI** with uniform random human sample | PPI CLT interval |
| E3 | **PPI++** (power-tuned λ) | PPI++ interval |
| E4 | **Stratified PPI++**: strata from panel agreement (e.g. unanimous / split) or user strata, with proportional or Neyman allocation | stratified interval |
| E5 | **Active inference** (Zrnic & Candès): inverse-probability-weighted estimator with item-specific sampling probabilities π_i | as in the paper |
| E6 | **Sequential/anytime-valid** versions of E1, E3 and E5: confidence sequences (betting or empirical-Bernstein) and the Sfyraki & Wang Freedman-based bound for the active sequential case | time-uniform |

- Cross-check E2/E3 against `ppi_py` on random inputs (results must match to numerical tolerance).
- Paired differences between two systems and win rates must use the paired structure (same items).
- Ratio estimands (precision, recall, F1) are **not** means. Implement via the delta method on a vector mean, and separately via a percentile bootstrap of the PPI estimator; ship only the ones that pass coverage.

### 6.2 Routing policies (all produce known sampling probabilities)

| id | policy |
|---|---|
| R0 | uniform random |
| R1 | stratified by panel agreement (fixed allocation) |
| R2 | active by single-judge uncertainty (1 − max confidence) |
| R3 | active by **panel disagreement** (vote entropy / variance) |
| R4 | active by a **learned error predictor** (a small logistic model, trained online on human labels so far, predicting "judge wrong"; probabilities updated only between batches and logged) |
| R5 | mixture: (1−ε)·uniform + ε·R3, ε tuned online with the FTRL approach of Sfyraki & Wang |

All active policies enforce a minimum probability floor (e.g. π_i ≥ 0.1·budget/N) so inverse-probability weights stay bounded; the floor is a documented parameter.

### 6.3 Tests

- Unit tests per estimator against hand-computed examples.
- Hypothesis-based property tests: estimates are invariant to item order; E2 equals E1 when the judge is useless and λ=0; intervals shrink as n grows.

**Checkpoint 2:** a notebook showing all estimators and policies on a synthetic task with a known truth.

## 8. Phase 4 — Coverage validation (the gate) (~3 days, CPU)

Before any study claim, prove the library's intervals are valid.

- For every (task, estimand, estimator, routing policy, budget n ∈ {50, 100, 200, 400, 800}), run **R = 2,000** Monte Carlo replicates: draw human labels according to the policy from the hidden truth, compute the interval, check whether it contains the full-human value.
- Report empirical coverage with its Monte Carlo standard error (≈ 0.5 percentage points at R=2,000 and 95% nominal).
- **Pass rule:** coverage ≥ 0.95 − 2·MCSE for every configuration exposed by default. Failures are listed in `results/coverage_failures.json`, explained, and either fixed or excluded.
- Sequential methods: simulate a researcher who checks after every label and stops when half-width ≤ target; measure coverage **at the stopping time**. Do the same for "peeking" with fixed-sample intervals (E2/E3 re-checked after every label) to measure the inflation; this is Finding F2.
- Also run on **synthetic stress cases**: a judge that is right 99% of the time on easy items and 30% on hard ones; a judge biased toward one class; a judge whose confidence is miscalibrated (confident when wrong).

**Checkpoint 4 (gate):** coverage table; any failures and what was done about them. Raihan approves before Phase 5.

## 9. Phase 5 — Pre-registration and the main study (~3 days, CPU)

### 9.1 Pre-registration (`docs/preregistration.md`, committed before running Phase 5)

- **Primary metric:** *human-label savings at equal precision*: for a target half-width w (per task, set to the half-width a 400-label human-only sample achieves), the number of human labels each method needs to reach w, relative to human-only (E1+R0). Reported as a ratio with a bootstrap CI over replicates, and pooled across tasks with a random-effects summary.
- **Secondary:** coverage; mean half-width at fixed budgets; judge-only error (|E0 estimate − truth| and its coverage); peeking inflation; cost in dollars per valid estimate (judge cost + human cost at a stated $/label for each task, with a sensitivity range).
- **Hypotheses (open, either outcome is reported):**
  - H1: PPI++ (E3+R0) needs fewer human labels than human-only on most tasks.
  - H2: panel-disagreement routing (R3) needs fewer labels than uniform (R0) under E5. **Prior evidence (Sfyraki & Wang) suggests this may fail; the result is reported either way.**
  - H3: stratification by panel agreement (E4+R1) captures most of the benefit of active routing with simpler assumptions.
  - H4: judge-only estimates (E0) miss the true value outside their own interval on a majority of tasks.
  - H5: a multi-judge panel gives larger savings than the best single judge as the prediction.
- Commit, record the hash in `docs/decisions.md`.

### 9.2 Runs

All estimator × policy × budget combinations from Phase 4 that passed, plus panel variants (best single judge, cheapest judge, full panel), with R = 2,000 replicates. Results to `results/study/*.json`. Parallelise across CPU cores; checkpoint progress so long runs can resume.

### 9.3 Analyses

- Savings ratio per task and pooled; a forest plot.
- When does routing help? Relate R3's gain over R0 to measurable task properties: judge accuracy, how concentrated the judge's errors are (does disagreement predict error? report AUROC of each routing signal for "judge wrong"), class imbalance, label space. This turns a yes/no answer into guidance.
- Calibration of judge confidence per task (reliability diagrams, ECE).
- Alternative Annotator Test results where tasks have multiple human raters.
- Cost analysis: dollars to reach target precision for each method, with judge and human costs separated.

**Checkpoint 5:** results summary, figures, and a one-page "what the evidence supports" note for Raihan's approval before writing.

## 14. Risks

| risk | handling |
|---|---|
| Routing gives no gain over uniform (as Sfyraki & Wang found) | Pre-registered as open; report it; the task-property analysis (9.3) still gives guidance; the toolkit's value (valid estimates + stopping) stands |
| An estimator fails coverage | Phase 4 gate; not shipped by default |
| Ratio estimands (F1) are hard to make valid | Delta method and bootstrap both tested; ship only what passes; document |
